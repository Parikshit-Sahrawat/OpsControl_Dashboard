# PostgreSQL schema/model reconciliation

The 32 drift groups previously reported on `feature/customer-department-rbac` were differences between SQLAlchemy metadata and the schema already established by migrations. They are resolved by correcting the models to match those contracts. No new migration, schema DDL, row updates or production access is required. The head remains `0025_provider_department_rbac`; historical migrations are unchanged.

## Impact inventory and resolution

Alembic counts an index replacement as separate removal and addition operations, so the group count exceeds the number of affected declarations.

| Original groups | Contract | Correction | Authoritative migration |
|---|---|---|---|
| 6 | Session-token and ETL-correlation uniqueness | Preserve the named unique constraint and separate nonunique lookup index for each table; remove combined `unique=True, index=True` declarations | `0012_identity_and_memberships`, `0008_correlation_engine` |
| 7 | Notification queue, open-alert deduplication, collector scheduling/latest runs, infrastructure latest evidence, ETL execution identity, remote-job customer lookup | Declare all existing indexes, including uniqueness, partial predicates and deterministic descending order | `0006_alert_state`, `0015_remote_jobs`, `0018_pentaho_execution_identity`, `0022_runtime_query_indexes` |
| 1 | Metric customer lookup | Remove the undeployed standalone-index declaration. Existing `(organization_id, observed_at)` B-tree supports the same customer-prefix lookup and time-window queries without another write-maintained index | `0005_metric_samples` |
| 6 | Rule definitions/activation details, remote job/evidence payloads, worker egress host/CIDR lists | Declare the existing PostgreSQL JSONB type. Other JSON columns retain their existing JSON type | `0013_security_controls`, `0015_remote_jobs`, `0017_rule_catalogs_activation` |
| 4 | Template attachment lookup names | Declare the existing `ix_template_attachment_*` names instead of autogenerated replacement names | `0010_template_attachments` |
| 2 | Template version ownership | Declare the existing template foreign key's `ON DELETE CASCADE`; existing ORM delete-orphan behavior remains | `0009_monitoring_templates` |
| 6 | Audit actor/customer lookup and chronological paging | Preserve original names and declare both existing chronological indexes, without dropping audit indexes | `0013_security_controls`, `0022_runtime_query_indexes` |
| **32** | **Total original groups** | **Zero remaining comparison differences** | **No migration changes** |

SQLAlchemy continues to deserialize JSONB payloads to the same dictionaries/lists. This correction does not change API contracts, resource ownership or effective permissions. Customer-scoped resource queries retain their existing composite indexes. Unique session tokens, one open alert per rule, unique non-null provider execution IDs and stable latest-evidence ordering are explicitly represented in metadata.

## Regression protection

`backend/tests/test_schema_contract.py` contains six regression tests for unique constraints versus lookup indexes, partial index predicates, descending timestamp/UUID ordering, deployed index names, JSON versus JSONB, and template-version cascade behavior. These cover semantics that Alembic autogeneration does not comprehensively compare, particularly index predicates.

`backend/scripts/access_schema_probe.py` now rejects any differences across all 50 application tables, checks that indexes are valid, and retains the separate ten-table access/user comparison. `scripts/access-acceptance.py` also executes the real `alembic check` CLI on its populated migrated fixture. It must report `No new upgrade operations detected.` The same gate runs in the existing access architecture CI workflow. The clean Docker demo gate independently executes `alembic check` inside the rebuilt API image.

The [schema evidence](../screenshots/access-management/schema.json) records zero application-schema drift. The [implementation report](ACCESS_IMPLEMENTATION_REPORT.md) contains security/browser, operational, restore and Docker acceptance results. The [validation manifest](../screenshots/access-management/validation-manifest.json) identifies tested source hashes.

## Local verification

From the repository root, with the documented backend virtual environment and Docker Engine running:

```bash
(cd backend && .venv/bin/python -m unittest discover -s tests -v)
backend/.venv/bin/python scripts/access-acceptance.py
python3 scripts/access-docker-demo.py
```

The acceptance script creates and destroys only its own PostgreSQL fixture, validates a populated `0024` to `0025` migration and runs the full schema comparison. Add `ACCESS_BROWSER_ACCEPTANCE=1` after installing the browser prerequisites in the implementation report to run the browser journeys too.

For an already running local Docker demo on this feature branch:

```bash
docker compose -f docker-compose.demo.yml exec -T api alembic current
docker compose -f docker-compose.demo.yml exec -T api alembic check
```

Rebuild the API image before this comparison so it includes the corrected models. `alembic check` inspects schema metadata; it does not apply DDL or alter rows. This correction requires no data migration or special rollback operation. Reverting these model changes would reintroduce drift and must not be followed by applying an autogenerated destructive migration. The existing additive access migration's protected rollback contract remains in force.

## Acceptance ownership

The owner accepts the single-provider runtime and is performing independent security review and UAT locally. Automated fixtures do not certify those reviews. No production deployment or production data modification is needed for this reconciliation, and none is performed. The feature PR remains subject to review and merge approval.
