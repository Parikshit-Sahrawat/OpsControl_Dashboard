# Page-by-page redesign specification

All rows are **proposals pending owner approval**. Current implementation and evidence are in [CURRENT_UI_AUDIT.md](CURRENT_UI_AUDIT.md). Common pattern: title and primary action in header; compact filters below; bounded paginated list; accessible detail; loading, empty, error, forbidden and stale states; responsive internal table scrolling with an obvious cue. Preserve the existing backend-enforced permissions and customer/environment scoping.

| Page | Purpose and information hierarchy | Proposed actions, filters and detail | State/RBAC/responsive requirements |
| --- | --- | --- | --- |
| Dashboard overview | Cross-domain health, freshness and incident summary; cards lead to actual records. | Scope and environment filters; read-only links to existing operations. | `overview.view`; explain unavailable/unknown values, never equate HTTP success with monitoring health. Compact cards at narrow widths. |
| Resource Management → Organizations | Customer organization directory and identity, separate from internal departments. | Search/paginated list; approved create/edit action in header if current route and permission support it; detail with associated resources. | Customer permissions; no department-based ownership inference. Zero-scope and forbidden remain distinct. |
| Resource Management → Data Sources / Resources | Canonical VM/ETL/API resource inventory and onboarding. | Existing domain tabs, search/customer/environment/status filters, create in page header; detail/drawer and links to integration/collector config. | `resources.*`; display configuration state separately from observed health. Keep eight-stage ETL integration workflow. Compact, scrollable columns. |
| Resource Management → Collectors | Configure collector identity, source ownership and lifecycle. | Existing create/edit form; collector list and detail; explicit configured-method list and Add Method action. | Existing `collectors.*` and source permissions; preserve revisions, fencing and method-specific identity. No implied agent installation. |
| Resource Management → Collection Methods | Manage one collector's independently added methods. | Dedicated method form, save into list, repeat; permitted edit/enable/disable/remove with confirmation. | Method authority from current backend; avoid checkbox substitute, show logs/metrics/traces separately. Keep errors adjacent to fields. |
| Resource Management → Event Parameters / Alert Rules / Notification Delivery | Existing policy/configuration functions. | Preserve existing edit flows and permissions; decide final subgroup label before moving. | Distinguish policy configuration from operational Alerts. No new template route without implementation evidence. |
| Access Management → Employees | Internal workforce and direct/inherited access context. | Paginated search, single contextual Create Employee in header, detail/editor; exactly one department for new employee, preserve legacy multi-membership display. | Existing `access.*`; explain denied action and revision conflicts; forms show customer grants separately from department membership. |
| Access Management → Departments | Provider teams and inherited roles. | List, one Create Department header action, role/delegate details. | Never present departments as customer organizations. Remove duplicate visible create placements after testing. |
| Access Management → Roles & Permissions / Organisational Access / Access Audit | Roles, direct/inherited projection, customer grants/restrictions and audit. | Make current boundaries/grants findable; filters and detail for audited changes. | Preserve LIMIT/DENY/DELEGATE/ALL semantics and last-admin protection. Independent `audit.view` visibility. Do not invent grants. |
| Data Pipelines: Inventory, Execution History, Schedule Monitoring, Evidence Review, Recovery Tracking, Incident Correlation | Operational evidence, status, review and recovery, with six existing pages preserved. | Existing filters, pagers and drawers; header refresh; links to canonical config only. | `etl.view` plus action-specific permissions; inventory also `resources.view`; distinguish UNKNOWN/INCOMPLETE, native schedule authority, retry outcomes and original failure. Mobile tabs must be discoverable. |
| Compute Instances / API Endpoints | Resource-backed operational health, freshness, history and evidence. | Domain filters, compact list and detail. Existing legacy compatibility view remains reachable until usage/test review. | `resources.view`; no duplicate resource registration. Stale health must not appear healthy. Internal scroll cue at mobile widths. |
| Alerts / Incidents / Reports | Operational triage, native incident lifecycle and existing reports. | Maintain separate current functions; decide sidebar grouping without replacing pipeline Incident Correlation. | Existing `alerts.view`, `incidents.view`, `reports.view` and mutation permissions. An unauthorized viewer's incident permission notice is expected. |

The table describes desired presentation of already implemented flows. Any proposed organization-create placement, independent Collector/Organisational Access route, or deep-link change must be validated against actual API contracts and separately approved before implementation. A screenshot alone does not prove missing persistence, authorization or backend functionality.
