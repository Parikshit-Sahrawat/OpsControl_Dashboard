## 1. Template applicability: what actually works and what does not

**Compatibility (PARTIAL / BLOCKED_DECISION).** `backend/app/services/template_resolution.py:attach_template` checks source existence, excluded-platform rejection, committed template/version, configuration shape through schemas, source row locking and duplicate current attachment handling. It does **not** evaluate Windows versus Linux, an allowed source-family/method matrix, resource attributes beyond missing-required values, or a versioned applicability predicate. `MonitoringTemplate.scope` is descriptive text; the `scope is None` check does not implement tenant/platform compatibility. An attachment can be stored before its rules fail provider-specific activation validation. Package create/update marks COMMITTED after container-shape checks, not a complete cross-component/OS semantic review. Invalid/excluded formats are rejected; that is not complete OS/method applicability. Missing: typed/versioned applicability and shared validation at attach/update/preview/apply, including changed source attributes. Required policy decisions are in S01-D1; ordinary enforcement code follows that decision.

**Existing host validation is reusable.** `backend/app/telemetry/api.py:template_defaults` translates supported FILE/JOURNALD/WINDOWS_EVENT log rows into explicit FILE_LOG method drafts, substitutes attributes and invokes existing `validate_method(..., host_os(source))`. Unsupported log-source mappings produce warnings; `saved:false`, `deployed:false`. This is a useful OS/method boundary, **not** general template-attachment validation or automatic activation. `backend/app/telemetry/configuration.py` has strict method schemas and pinned runtime generation. Do not infer complete host/process/service/API package translation from the presence of that adapter.

**Version pins and overrides (IMPLEMENTED_VERIFIED within current contract).** Package commits add `MonitoringTemplateVersion` rows; row locking serializes version allocation. Attachments store an explicit integer version; existing resource edits preserve v1 after v2 is committed (`templateAttachmentSelection.js`). Overrides survive save/reload. `resolve_data_source_configuration` merges attachments by priority then UUID, recursively merges collector objects and named component rows, then applies DataSource `opscontrol.monitoring_overrides`. Required attributes and collector-type conflict descriptions are returned. Actual PostgreSQL/HTTP/browser tests prove pinned version retention, overrides, deterministic current resolution, malformed package rejection and rollback after an injected attachment update failure. This **does not** establish approved ETL Template→Workflow→Job precedence, immutable override history, semantic conflict resolution or OS compatibility. Equal-priority UUID ordering is implemented behavior, not evidence of a separately approved business precedence policy.

**Effective generation / preview (PARTIAL).** `GET /api/v1/monitoring/data-sources/{id}/effective-configuration` returns a redacted current resolution. The resource editor's preview is explicitly **saved effective configuration**, not unsaved-draft authoritative validation. `valid` means no missing required attributes; it is not full runtime or applicability validation. `backend/app/unified/api.py:preview/save_parameters/activate_parameters` separately supports validated versioned resource parameters, and telemetry APIs separately generate/validate/apply collector configurations. Those existing stores must be reused where appropriate, but they are not a complete template command/revision/provenance chain. Template-derived activation rules carry no catalogue rule version ID; the activation plan fingerprint hashes the generated collector/rules, not a retained attachment-set revision. A semantically identical newer template cannot thereby be assumed to have distinct historical application provenance; this is a source observation, not a newly executed runtime test. A new competing configuration owner would be wrong.

**Activation / persistence (PARTIAL).** Attachment persistence works and never certifies health. `activation_engine.build_plan/_rules` provides provider-specific HTTP/infrastructure metric/rule checks, scoped active worker and missing-prerequisite rejection; `activate` compares fingerprint, serializes source updates, starts collector STOPPED and mutates one current activation. Telemetry `save_version/apply` requires actual binary validation and a registered agent, and diagnostics distinguish desired/applied/verified/evidence. These are real existing mechanisms, not absent features. Missing is a reviewed, uniform template-derived draft→validated effective revision→approved desired/application state→exact collector acknowledgement/evidence linkage. No genuine positive provider activation is certified here. A frontend-only Save or VALID badge cannot close this contract.

**Tenant and permissions (IMPLEMENTED_VERIFIED for tested source-owned operations).** Attachment ORM scope follows DataSource→organization; middleware maps mutations to `templates.manage`, reads to `templates.view`; before-flush ownership checks and fresh request authorization remain. Actual viewer403, scoped cross-customer404/403, revoked stale token401, concurrent revocation denial and rejected protected fields are in `v16_api_probe.py`, `sprint08_http_probe.py`, `sprint1_resource_security.mjs`. Templates and package versions are intentionally **global**, without `organization_id`; shared catalogue mutation is platform-admin controlled. A shared catalogue being visible to authorized `templates.view` users is not evidence of a tenant leak. Customer-private template catalogues would need an explicit requirement/decision, not an invented tenant filter.

## 3. Configuration compatibility and concrete code gaps

The new source-template panel commits separately from resource identity Save/Cancel. A failed later operation does not atomically undo earlier successful requests. Existing single-request rollback test is not a multi-step atomicity proof. Required decision S01-D3: atomic source-owned command versus explicitly documented staged/draft operations with visible partial result/recovery; do not silently promise all-or-nothing.
- **Old/new formats:** inspect `legacy_template_attachments`, `opscontrol.monitoring_overrides`, attachment overrides and parameter `configuration.overrides` separately. Do not silently normalize or backfill ambiguous precedence/ownership. Approved migration preservation remains mandatory; expected failures and schema constraints are known, but new history migration/backfill/fence is not implemented/tested.
