# Database preservation and recovery

No schema/data mutation or new forward migration is introduced. Applied0038 and all earlier migrations remain byte-identical. Legacy cluster, cluster association and association decision tables/models remain present with their existing RESTRICT foreign keys and scope fences. DataSource, Collector, InfrastructureEvidence, receipts and audit history are not deleted. Retaining ORM metadata avoids accidental schema-diff drops.

Destructive schema retirement is BLOCKED pending an independently reviewed export and relationship inventory. Do not access production or parallel UAT. In a separately owned disposable PostgreSQL clone, inventory counts and keys in all three cluster tables, linked organizations, sources, collectors, evidence and audit records. Freeze writers; use a consistent transaction/snapshot for an encrypted full database backup and tenant-attributed export, with schema revision, row counts, stable keys, checksum manifest, access controls and retention owner. Verify restoration to a second owned database and compare counts, keys, relationships and immutable decisions before considering any new forward migration. Shared provider identities may have several explicit customer associations: export all grants; never pick one inferred owner or cascade unrelated data.

Rollback of this code change does not require data restoration because no data was changed. It re-enables excluded capabilities and therefore requires owner authorization. Any eventual schema removal needs a separate forward migration with refusal on unexported/ambiguous references, an explicit recovery procedure, and fresh/populated upgrade tests. Fresh/PostgreSQL preservation and restore tests were NOT RUN in this task; no preservation execution PASS is claimed. No production/UAT database was queried.
