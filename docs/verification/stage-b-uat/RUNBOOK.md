# Stage B UAT runner, deployment and recovery runbook

This runbook controls **only** a persistent, provider-owned Ubuntu Docker Compose UAT project. It does not grant deployment approval or certify the existing environment. Do not use the repository demo Compose file or Sprint 14 disposable reset script as the persistent UAT base.

## One-time operator setup (before pilot)

1. Register a dedicated self-hosted Ubuntu x64 runner labeled `opscontrol-stage-b-uat`. Limit repository access and filesystem permissions to its UAT operator account. Docker group membership is root-equivalent: dedicate the host, restrict runner administration, and do not run unreviewed feature-branch workflows on it. Set the runner marker `/etc/opscontrol/stage-b-runner-approved` only after the host/project boundary is reviewed.
2. Create GitHub environment `stage-b-uat-migration` with required independent reviewers and **prevent self-review**. Protect who can change environment reviewers, runner labels and repository variables. The workflow checks these settings and refuses to operate if they are absent. Keep `STAGE_B_UAT_ENABLED=false` and `STAGE_B_UAT_RECORD_MAIN_ENABLED=false` until the controlled pilot is witnessed and recorded.
3. Set runner-service environment variables, not repository files: `STAGE_B_UAT_BASE_COMPOSE` (absolute operator-owned Compose path outside the checkout), `STAGE_B_UAT_PROJECT` (`opscontrol-feature-uat-...`), `STAGE_B_UAT_STATE_DIR` (private 0700 durable directory), `STAGE_B_UAT_BACKUP_ROOT` (private backup directory), `STAGE_B_UAT_API_URL`, `STAGE_B_UAT_FRONTEND_URL` and `STAGE_B_SMOKE_CONFIG` (private 0600 synthetic-account JSON). The workflow sets `STAGE_B_AUTH_SMOKE` to the trusted main checkout's `scripts/uat/stage_b_smoke.py`. Set repository variable `STAGE_B_RUNNER_MARKER=opscontrol-stage-b-uat` and `STAGE_B_UAT_PUBLIC_API_URL` for the frontend build. Do not expose passwords, tokens or private keys in workflow inputs or logs.
4. The existing UAT Compose must define `postgres`, `api`, `worker`, `frontend`, and a one-shot `migration` service. Keep all UAT-owned DB volumes, networks, secrets, CSP overrides and fixture mounts in that base. Compose runs with the base file's parent as its project directory so existing relative mounts and `.env` resolution stay tied to the UAT-owned configuration. The migration service uses separately authorized DDL credentials and must not publish ports; API/worker use their existing least-privilege identities. The worker must have an explicit worker command. Bind mounts must not replace immutable application code. Review `docker compose config` **privately** because it can contain secrets; never upload its raw output.
5. Confirm PostgreSQL already runs in that exact UAT project; record its volume ID, migration revision, row counts and fixture identifiers. Review a recent custom-format backup and independently restore it into a disposable empty database. Store the archive and `sha256` manifest privately, using `backend/scripts/database_backup.py` where appropriate. The deployment script checks archive integrity and age; the independent restore is an operator acceptance step, not inferred from `pg_restore --list`.
6. Install Python 3, Docker Compose v2, `gh`, `pg_restore` matching the UAT PostgreSQL major, and the configured CA/proxy trust on the runner. Verify GHCR pull rights. Do not give the build job UAT network or secrets. Review the chosen source SHA, Dockerfiles, migration diff and GitHub CI before authorizing it.

The private smoke JSON must name two **synthetic** customer UUIDs and a read-only user authorized only for the first:

```json
{"api_url":"https://uat.example.invalid","viewer":{"username":"synthetic-viewer","password":"FROM_PRIVATE_FILE"},"viewer_customer_id":"00000000-0000-0000-0000-000000000001","other_customer_id":"00000000-0000-0000-0000-000000000002"}
```

This is a shape example, not a usable credential or fixture. Use a 0600 file outside the repository; the configured UAT identities must actually exist. No live monitoring state is implied by synthetic data.

## Controlled pilot and ongoing operations

1. Keep both repository enable variables false. Capture preflight state, source SHA, reviewed branch, UAT project/volume identity, backup checksum, independent restore result, migration diff/review and protected environment reviewer. If any is missing, stop.
2. For the first witnessed pilot, an authorized operator runs the **reviewed trusted main** driver manually on the dedicated runner with digest-built images. Use `scripts/uat/stage_b_deploy.py status --state-dir "$STAGE_B_UAT_STATE_DIR"` first. The `deploy` command requires the exact branch, SHA, backend/frontend `@sha256` images, migration hash, project/base Compose, approved request, backup path/root, independent migration reviewer/ref, API and frontend URLs. Its one-shot migration is separate from API startup. Never run feature-branch scripts on the runner.
3. Record API/DB, frontend, auth, RBAC negative and monitoring smoke results; compare DB counts/volume IDs; perform independent browser UAT. Simulate an incoming main commit by `record-main` and verify the current feature SHA stays unchanged; then witness `release`, deploy only the latest pending main SHA, and confirm the new current SHA. Check all persistent fixtures remain intact. Capture GitHub run IDs, immutable image digests, migration revision, backup checksum, smoke logs and reviewer identity in the change record.
4. Only after that complete pilot is accepted, set `STAGE_B_UAT_ENABLED=true` for protected **manual** workflow dispatch. Enable `STAGE_B_UAT_RECORD_MAIN_ENABLED=true` separately for record-only push observation. Main push never deploys. Operators select `deploy_feature` with an exact reviewed branch tip and SHA. They later dispatch `release` and `deploy_main` with the latest pending main SHA. `feature_mode` starts the next Feature UAT cycle. `maintenance` freezes deployments. Operations are serialized and state transitions are audited.
5. A migration hash change requires a recent verified backup, independent source/migration review, another environment approval and a distinct reviewer. If migration safety is uncertain, do not dispatch. There is no unattended destructive migration or automated restore.

## Failure and recovery

If image pull, migration, Compose update or smoke fails, the driver records the attempt and moves policy to `MAINTENANCE`. Current/last-verified state is **not** a claim that containers or schema remain unchanged. Leave the database and volumes intact; inspect Compose service state, logs, `alembic current`, backup manifest and row counts. Decide whether an application-image rollback is safe with the possibly advanced schema. An authorized operator may redeploy a previously verified digest only after checking compatibility; database restoration requires a separate reviewed recovery change and an empty/disposable target where applicable. Once independent UAT confirms actual health and data preservation, clear the failure using `stage_b_state.py recover --state-dir ... --approval-ref ...`, record the evidence, and resume the required mode. Never use `docker compose down -v` or reset the UAT database.

## Stop/inspect commands

Use `python3 scripts/uat/stage_b_deploy.py status --state-dir "$STAGE_B_UAT_STATE_DIR"` for policy state. On the UAT runner, use `docker compose --project-name "$STAGE_B_UAT_PROJECT" --file "$STAGE_B_UAT_BASE_COMPOSE" ps` and `logs --tail=100 api worker frontend` for inspection. To stop only application services under an approved maintenance window, use `docker compose ... stop api worker frontend`; do **not** stop/remove PostgreSQL as part of ordinary Stage B operations. There is no Stage B reset command.
