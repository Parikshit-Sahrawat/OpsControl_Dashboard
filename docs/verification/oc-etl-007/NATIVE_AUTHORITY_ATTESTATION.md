## Existing versus qualified identities

PipelineJob UUID and its (integration,native_id) key, canonical Resource→JobOrder→Workflow ownership, source UUID/generation, method revision/connection/capability and reader hash are retained. Resource/Job display names are not durable authority. Existing reader capability RUNTIME_VERIFIED labels prove their existing reader contract, not a cross-method namespace alias or owner UAT. The isolated lab inventory records exact synthetic tuples and sources; it is not inventory from production or owner UAT.

An immutable claim version still records the original operator namespace. A qualified attestation separately binds it to `(organization, environment, platform, canonical_authority_id, object_kind=JOB, canonical_object_key)`. SHA-256 of this ordered JSON tuple is the canonical target key. Signed authority_aliases must include the claim, and observed_native_id must equal the persisted native Job identity. Alias strings alone, name equality or timestamps are insufficient. Distinct aliases signing the same canonical tuple resolve to one key; a partial unique SQL index reserves only one current qualified owner. Cross-surface native-ID extraction and genuine alias correctness remain provider-verifier obligations, not inferred normalization.

## Envelope and evidence requirements

Envelope fields: issuer_key_id, strictly typed body and Ed25519 signature. Body fields: schema_version1, assurance (PROVIDER_QUALIFIED or CONTRACT_TEST_ONLY), organization_id/environment/platform, exact staged binding UUID/native Job UUID/observed native ID, canonical authority/object key, signed authority aliases, object_kind JOB, issued_at/not_before/expires_at and explicit method proofs. Unknown fields refuse.

Every method proof names method/source/generation/revision/reader_definition_hash, original accepted evidence UUID/payload SHA-256 and exact_build. Backend compares the current authorized method/source and immutable binding snapshot, current existing eligible reader profile, same-customer accepted AUTHENTICATED_RUNTIME evidence/native ID/source generation/hash, and profile version/build. Original evidence observed/created timestamps must be inside the signed [not_before,issued_at] window. Missing/stale/unknown/mismatched evidence refuses. These checks do not invent provider-specific epoch, repository or build semantics.

Signature input is `b"opscontrol/native-authority/v1\x00"` plus UTF-8 `json.dumps(AuthorityBody.model_dump(mode="json"), sort_keys=True, separators=(",",":"), ensure_ascii=True)`. UUIDs/timestamps use the parsed model's canonical representation. Signature/public key are strict base64 Ed25519 bytes. Algorithm is fixed; no caller-selected cryptographic algorithm. Cryptography50.0.2 is pinned for this functionality. Added dependency/transitive license review and independent security clearance remain separate gates.

Expiry policy v1: offset-aware clocks, not_before ≤ issued_at ≤ evaluated_at < expires_at and maximum not_before→expires_at86400 seconds. Future/naive/unbounded/expired proof refuses. This security TTL is unrelated to a Workflow recurrence/calendar. Signature is rechecked against current trust configuration; source generation/reader revision changes invalidate it. Revocations are append-only DB events, serialized with source admission via source row locks. Expiry/revocation are also checked by deferred receipt/confirmation constraints; current admissions revalidate trust immediately before commit. External trust-file replacement is not an atomic distributed DB transaction: drain writers and record DB revocations before key removal/rotation. No claim of atomic filesystem revocation or exactly-once delivery.

## Trust boundary and genuine qualification

`OPSCONTROL_ETL_AUTHORITY_TRUST_STORE` points to a server-managed non-symlink JSON file, owner root/service UID, no group/other writes, protected parent directory and bounded size. It contains **public keys only**; private verifier keys never enter the application or browser. Default is unconfigured/blocked. Minimal empty configuration is `{"version":1,"issuers":{}}`; there are no built-in qualified keys/targets.

Issuer entries contain public_key_base64, assurance, revoked and exact targets keyed by canonical target SHA-256. Qualified targets require an accountable approval_reference plus exact_builds and source_ids matching the signed method set. No wildcard interpretation. Only an explicitly provisioned PROVIDER_QUALIFIED issuer and approved exact target can attempt admission; current runtime evidence validation is still mandatory. Issuer/target approval references must refer to genuine independently reviewed exact-build read-only evidence. The application cannot determine truth merely from an operator typing such a reference; trusted configuration/verifier governance is an explicit prerequisite.

CONTRACT_TEST_ONLY issuers can produce `CONTRACT_VALID_NOT_QUALIFIED` previews. They cannot persist an attestation, create qualified ownership, confirm or activate. Signing a PROVIDER_QUALIFIED body with a test issuer refuses. All keys provisioned by this task's disposable harness are test-only, all targets empty. **No positive provider attestation or qualified DB row is seeded.** Mathematical signature validity and canonical-key equality tests are not genuine-provider qualification.

## Secured operations

POST `/api/v1/etl/native-authority/validate-envelope`: scoped etl.configure, signature and binding/method/source context; no persistence/activation. POST `/attestations`: distinct reviewer from the stager, genuine qualified issuer/target and current runtime evidence; append-only scoped attestation, hash deduplication and domain audit. POST `/attestations/{id}/revoke`: existing etl.configure, scoped source locks and append-only audited revocation. Existing binding CONFIRM accepts attestation_id and revalidates the exact staged version before appending CONFIRMED + qualified ownership atomically. No auto-selection, automatic collection start, provider execution permission or Workflow activation.

Signed proof for a previous stage cannot be reused for a newly staged replacement. A confirmed successor retains its original staged-proof reference. Qualified owner conflicts roll back the entire transaction. Retiring a quiescent confirmed version closes its qualification at the same validity boundary, preserving all records. Active or stale-generation replacement remains blocked pending reviewed proof/cutover qualification.
