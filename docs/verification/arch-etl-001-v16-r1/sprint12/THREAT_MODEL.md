# Bounded shared-resource threat model

One scenario only: customer A Application A and customer B Application B need one canonical shared VM, observed by a provider collector. Actor AB has explicit A+B access, actor A only A, actor none neither. Assets include customer-specific telemetry, resource identities, source generation/checkpoint, graph edges, incident root evidence and notification destinations. The positive two-view shared association is blocked by the current schema; threats below are tested only to the extent listed.

| Threat | Trust crossing and attack | Existing control or controlled observation | Remaining gap / priority |
|---|---|---|---|
| TM-01 IDOR across customer IDs | A-only actor changes selection or resource/detail ID to B | `choose` intersects requested and authorized UUIDs; ORM scope and direct resource lookup yield no B row/404 in fixture | HTTP-level B inventory/detail and cursor forgery in this exact fixture not rerun; prior Sprint 08/09 authenticated acceptance inherited. P0-03 |
| TM-02 Shared VM identity duplication | Register same physical VM separately in A and B or alias weakly by name | Unique `vm_id`, scope guard and fixture deny a second foreign customer binding | Approved two-view association has no model/API. P0-03, AUD-06 relevance |
| TM-03 Forged dependency/relationship ID | B edge references A VM, or A actor points to B edge | Composite FK rejects B→A target; route checks customer/environment; direct scope guard blocks unauthorized resource | Cross-customer approved edge/projection and exact relationship-ID HTTP negative need future design/test. P0-03/P1-04, AUD-01/02 |
| TM-04 Telemetry laundering | Collector submits unauthorized method/signal or rewrites tenant attribution | Authenticated agent/collector/customer binding; method ID mismatch returns 422 in fixture | Missing method ID still accepted for explicit legacy compatibility; shared attribution and quarantine policy unimplemented. P0-02/P0-03, AUD-06 |
| TM-05 Scope-as-grant or role escalation | A-only employee selects B/ALL, or view actor mutates shared VM | Explicit grant intersection, separate permissions, denial and revision tests; fixture shows A-only cannot select B and view lacks update | Shared projection-specific view/mutation policy requires implementation. P0-03/P1-01 |
| TM-06 Derived graph/incident inference | A actor reads B identity through shared VM root/aggregate | Existing native incident inventory and detail are customer scoped; current dependency graph refuses cross-customer edges | No approved shared graph/incident projection yet; requires negative aggregate and root-evidence tests. P0-03, P1-04, AUD-07 |
| TM-07 Stale collector owner | Replayed old lease writes evidence/checkpoint after replacement | Existing owned PostgreSQL fence test rejects stale token; source generation preserved | Target multi-replica failure and shared physical source measured continuity unverified. P0-02 |
| TM-08 Credential/network compromise | Exposed agent token or forged provider network | Token digests, revocation/overlap, TLS design and ingress checks in code | Production CA, firewall/CNI, secret renewal and physical routes unverified. P0-05/P0-06, AUD-08 |
| TM-09 Wrong-customer notification | Shared incident routes B evidence to A recipient | Customer-scoped incident/destination models and fenced outbox in current code | Shared incident ownership and recipient policy absent; provider sandbox acceptance required. P1-07 |

The security invariant is fail closed on missing/ambiguous customer or source identity, while preserving previous defensible evidence. Do not create duplicate VM identities, relax scope/foreign keys or infer an ALL grant. This review is bounded static inspection plus a controlled PostgreSQL fixture; it is not a target deployment penetration test.
